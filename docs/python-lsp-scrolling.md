# 修复 warning 后的 Python 滚动复测

2026-09-17，日常配置基于 `4527a46`。本次只改进测量工具和记录，没有关闭或修改语法高亮、Neoscroll 动画、诊断、配对提示及引用高亮。

修复后的 `~/Projects/transformer/transformer.py` 已确认是 **0 条诊断**，但连续滚动仍有明显慢帧。LSP 引用高亮有开销；更突出的长停顿来自 `vim-matchup` 的重复配对查询。清掉 warning 没有单独解决这一问题。

## 修复前后的条件

当前文件为 240 行、10,706 字节。与此前记录的 237 行版本相比，只增加了 `encoding: Tensor` 声明及说明，共三行。项目现在也有 `pyrightconfig.json`，指定 `.venv`、Python 3.12 和 `standard` 检查模式。因此不能把诊断减少全部归因于源代码变化。

本机保留的 basedpyright CLI 历史记录中，该文件有 321 条 warning、2 条 error，包括找不到 torch 后产生的未知类型问题。指定项目环境后的中间记录已减少到 63 条 warning、2 条 error。当前主机上的 basedpyright、ruff、typos_lsp 均正常初始化并附着，文件诊断为零。

此前的 Python 性能测试运行在沙箱中，basedpyright 启动后退出，只有 ruff 与 typos_lsp 正常工作。因此，旧数据不能排除正常 LSP 和大量诊断的影响；对应历史报告已补充这一限制。

## 方法

所有性能测试顺序运行，使用相同的修复后源文件和当前项目配置。每个进程先等待 8 秒，要求三个 LSP 都初始化，并确认诊断为零；设置临时对照条件后再等 700 ms。每轮四段正反向滚动，每段 20 个真实 SGR 滚轮事件，间隔 8 ms；PTY 为 `xterm-kitty`、120 × 36。

控制指令通过独立 RPC 通道传送，滚轮仍从终端输入。最初使用命令行控制的探索批次会额外触发补全和 documentSymbol 请求，已弃用并全部重测；改成 RPC 后长停顿依然存在。

计时从写入输入开始，到 Neovim 对相应视口完成装饰重绘为止；另记输入解码时刻，区分排队等待和后续绘制。这不是物理触控板、kitty GPU、桌面合成器或显示器的延迟，也不是帧率。每段中的事件会相互排队，不能当作独立统计样本。

历史诊断仅在测试进程中新建的命名空间重放。行号按新增三行平移，列号转换为 UTF-8 字节位置。它隔离已有标记的绘制成本，**没有恢复旧项目环境、旧 LSP 分析或诊断发布负载**。隐藏诊断时记录仍保留，滚动条、状态栏等消费者仍可读取。

## 诊断与 LSP 对照

五种条件按交错次序各测四轮，各 320 个事件。分位数用最近秩 `ceil(n × q)`；以下为合并结果，单位 ms。

| 条件 | 中位数 | P95 | P99 |
| --- | ---: | ---: | ---: |
| 当前代码，0 诊断，三个 LSP | 54.55 | 298.04 | 312.40 |
| 同一代码，重放 321 warning + 2 error | 101.50 | 278.48 | 345.43 |
| 重放相同记录，仅隐藏下划线 | 65.17 | 251.67 | 267.69 |
| 重放相同记录，隐藏内置诊断装饰 | 36.49 | 306.51 | 322.87 |
| 当前代码，0 诊断，停止三个 LSP | 104.40 | 245.91 | 272.83 |

大量标记会增加部分成本，但不能从这组结果得出“黄线就是主要瓶颈”：去掉下划线或全部诊断装饰没有消除长停顿，零诊断和停止 LSP 时仍会卡。各轮波动明显，例如隐藏诊断后的四轮 P95 分别为 250.92、57.54、306.27、318.08 ms，不能只选最快一轮作为收益。

所有 1,600 个事件均通过输入计数、视口移动、高亮及源文件未修改检查。各观测窗口内诊断变化次数为零，没有重新请求诊断或语义 token；LSP 正常运行的每个条件累计发出 280 次 documentHighlight 请求。代码操作请求还包括滚动结束后 700 ms 等待期中的 CursorHold，不能全部算成连续滚动请求。

停止 LSP 会让引用高亮切换提供方，并移除对应语义 token，因此这一项是整个功能配置的对照，不能直接当作纯 LSP CPU 时间相减。

## 配对提示与引用高亮

另做两轮正反序对照，各 160 个事件。三个 LSP 始终保留，仅在临时进程中暂停指定功能。

| 条件 | 中位数 | P95 | P99 |
| --- | ---: | ---: | ---: |
| 当前完整配置，0 诊断 | 28.93 | 291.65 | 323.06 |
| 仅暂停 vim-matchup 配对提示，0 诊断 | 12.07 | 90.07 | 97.33 |
| 暂停配对提示，同时重放旧诊断 | 17.44 | 99.30 | 108.05 |
| 仅暂停 vim-illuminate 引用高亮，0 诊断 | 8.16 | 217.28 | 241.42 |

暂停配对提示的两轮 P95 均下降：217.37 → 83.74、305.24 → 93.02 ms，合并后减少约 69%。引用高亮暂停后，documentHighlight 请求由 140 次变为零，普通事件更快，但约 200 ms 的长停顿仍在。暂停配对提示后，重放旧诊断仍略慢于零诊断，说明诊断绘制确有额外成本；两轮样本不足以推算任意文件的固定收益。

Lua 采样定位到 `treesitter-matchup.internal.get_lang_matches`。额外计时在一段观测窗口内记录到 **42 次 `get_matches()`，累计 233.97 ms**；其中 **170.34 ms** 与首个滚轮输入至最后一帧的区间重合。这些调用每次都返回相同数量的 131 条配对记录。

当前配置的配对搜索范围为光标上下各 300 行，对这个 240 行文件相当于覆盖全文件。插件在寻找当前、前后及周围配对时会重复调用查询。配置里的 120 ms 延迟只推迟计算开始，已经开始的同步查询仍会占用 Neovim 主线程，让随后到达的滚轮事件排队。上述计时支持优先优化这些重复计算；它不意味着所有余下延迟都来自该插件。

本次暂停只是定位手段。实际配置仍保留配对提示、引用高亮、原有语法颜色和键盘滚动动画。

测量脚本新增 `--require-lsp`、`--prepare-lua`、诊断变化和请求计数。所需服务未初始化会明确失败。安装好的插件和工具复用，测试状态与 RPC socket 单独放到临时目录；文件内容在各次运行前后核对 SHA-256。

```sh
python3 scripts/benchmark-wheel-pty.py \
  --file ~/Projects/transformer/transformer.py \
  --runs 4 --bursts 4 --settle-ms 8000 \
  --require-lsp basedpyright --require-lsp ruff --require-lsp typos_lsp
```

脚本需要本机 Python `msgpack`，不会自动安装。应在能正常启动 LSP 的主机环境复跑。上面的命令测当前配置；诊断重放与单项暂停通过 `--prepare-lua` 使用记录中的对应脚本，并在测试结束时随进程消失。本页与旧报告的运行环境、控制方式不同，不作直接的修复前后百分比比较。

最终验证通过静态检查、生成的 Lua 探针语法检查、无准备脚本时的主机 PTY 双向滚轮检查，以及故意指定不存在的 LSP 时的失败检查。原项目文件的校验值始终一致。
