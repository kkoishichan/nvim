# 后续性能优化

本轮以 `3c148e1` 为基线，继续测量上一轮滚动修复后的热点。

## 颜色解析

滚动刷新前实时检查语言服务是否支持 `textDocument/documentColor`。没有对应能力时，不进入插件昂贵的版本查询与请求准备；动态增加、移除能力时立即重新判断，不缓存客户端能力。

CSS 变量解析沿用锁定插件的原始规则，按缓冲区和文本版本缓存结果，也缓存不存在的变量。同一变量不再为每个可见使用位置反复全文查找。修改、撤销和文件重读会使缓存失效；卸载、重载与关闭适配层时清理。缓存只在滚动的同步绘制期间使用，原有即时编辑刷新入口继续保留。

真实插件回归计数：一个包含有效及无效变量的视口，全文扫描从 42 次降至冷缓存的 2 次；随后滚动到六个新视口，全文扫描为 0 次。无客户端、无颜色能力及移除能力后均不调用原 LSP 流程；动态获得能力后，同一缓冲区的两个视口合计调用一次。

此项仍保留上游对迟到 `documentColor` 回复缺乏版本过滤的限制，并未引入完整 LSP 结果缓存。

## 滚动条与状态栏

滚动条的 virtual 模式会在每次刷新中统计折叠并建立行号映射，打开着的折叠很多时仍可能遍历全文。本轮保留原生几何算法，将自动刷新请求合并到固定的 16 ms 时间窗，持续输入时仍定期刷新；移除仅供旧版 Neovim 使用的重复滚轮入口。原生拖动、折叠操作和显式刷新继续使用原入口。

回归验证 300 次请求只进入一次上游调度，真实插件完成一次绘制；连续请求能够持续取得进展。关闭折叠时滑块变高，打开折叠后变短；全部标记来源及模式保持原样。另覆盖停用、重新启用和同时重载插件与适配模块时的旧定时器清理。这里的请求合并计数不是“原先实际绘制 300 次”的断言，上游本身也有异步合并。

状态栏锁定版本把事件参数 `scope` 写成了 `kind`，导致全局状态栏按分屏数量重复计算同一个活动窗口。适配层只纠正已知注册的参数，保留原事件和 16 ms 队列；实际组件计数由二分屏的 2 次、四分屏的 4 次，统一降为 1 次。文件名、模式与光标位置继续更新，独立窗口状态栏和不认识的回调保持原行为。

主题和背景变化由上游完成主题刷新，随后合并补修事件参数，避免重复执行主题初始化，或让后续主题切换覆盖优化。重载时清理旧实例排队工作。

## 完整配置测量

2026-09-15，Neovim 0.12.5，120 × 36 屏幕；同一依赖锁，AB/BA 两轮，每轮 80 个原生滚轮事件，剔除各轮前十个样本。普通代码及颜色代码为 3,000 行 Lua，CSS 场景为 1,000 行、重复使用同一颜色变量。每份配置每场景保留 140 个样本，P95 使用 nearest-rank 算法。

| 场景 | 基线中位数 | 当前中位数 | 基线 P95 | 当前 P95 |
| --- | ---: | ---: | ---: | ---: |
| 普通代码 | 4.73 ms | 4.83 ms | 25.32 ms | 19.72 ms |
| 含颜色代码 | 4.62 ms | 4.30 ms | 25.84 ms | 22.53 ms |
| CSS 变量 | 2.87 ms | 2.83 ms | 159.71 ms | 14.08 ms |

普通代码中位延迟基本持平，不能据此声称常规滚动整体明显加速。主要收益是慢帧减少：普通代码 P95 降低约 22%，CSS 变量场景约 91%。测量包含完整配置、屏幕网格及本地 RPC，记录视口移动后的第一帧；不包含物理输入设备、真实终端绘制及桌面合成器。三个场景均只附着 `typos_lsp`，不覆盖提供全文颜色响应的语言服务成本。

24 组快速回归全部通过；最后的生命周期修正再次通过静态、集成、状态栏、滚动条及四主题检查。实际 PTY 检查确认上下滚动和非当前分屏滚动时滑块跟随视口，另一分屏和焦点保持不变，新区域颜色正常，终端无错误。

完整样本、调用计数和终端快照见 [performance-followup-results.json](performance-followup-results.json)。本轮此前的探索采样仅用于筛选热点，未与最终交错测量混用。
