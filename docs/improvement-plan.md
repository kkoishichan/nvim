# Neovim 全面提升计划

审查日期：2026-09-05。基线提交：`bbf8a69`。本机版本：Neovim 0.12.5。

目标是把现有 IDE 工作流做得更稳定、流畅、容易维护。按用户选择采用平衡提升方案，沿用现有编辑习惯、主题与语言覆盖；具体语言的投入顺序可按日常使用频率调整。本文件是实施计划，运行配置尚未修改。

## 现状与实测

现有基础已经比较完整：lazy.nvim、原生 LSP 配置、Blink、Conform、Lint、DAP、Neotest、Overseer、Git、会话、AI 终端和文档预览均已集成；Mason 安装与普通启动分离，外部文件变化、敏感文件和浮窗生命周期也有专门处理。

| 项目 | 审查结果 |
| --- | --- |
| 插件锁 | 84 个条目；本机插件 HEAD 均与锁文件一致，未发现已跟踪文件的本地修改 |
| 配置规模 | `lua/` 下 54 个 Lua 文件，共 11,908 行 |
| 外部工具 | 54 个带版本的 Mason 包 |

启动测量使用已安装插件与 parser，缓存、状态、日志写入临时目录。每个场景启动四次，下表取后面三次的中位数；时间读取 `--startuptime` 的 `NVIM STARTED` 标记。

## 优先处理的发现

### 1. 长行保护漏判，颜色预览出现秒级开销

位置：`lua/user/plugins/performance.lua:25`、`lua/user/plugins/editor.lua:28`。

当前长行策略使用 `filesize = 0.01`，但本机锁定的 faster.nvim 实现先把 MiB 大小四舍五入至一位小数，再与阈值比较。约 30 KB 文件会变成 `0.0`，导致长行策略不触发。颜色预览的排除条件只检查大文件标记、总行数和总大小，也没有直接识别单条超长行。

实测该文件 `bigfile=false`；打开耗时约 6.3 秒。仅在临时启动包装中关闭 `nvim-highlight-colors`，耗时降至约 97 ms，支持将颜色扫描列为这一复现中的主要开销来源。

实施：统一以原始字节、行数和最大行长描述高成本 buffer；在昂贵扫描之前进行有界检测，不能为了判断长行先完整扫描整个大文件。颜色预览增加独立的长行限制，并按文件类型启用命名颜色和 Tailwind 识别。

### 2. 大文件的 LSP 降级存在时序和作用域问题

位置：`lua/user/plugins/performance.lua:1`、`lua/user/plugins/lsp.lua:457`。

约 2.5 MiB JSON 被标记为大文件，filetype 最终被清空，但后续快照仍能看到 `typos_lsp` 进程，输出也记录了 `jsonls` 启动后退出。证明当前降级未能阻止所有语言服务启动；本次没有把语言服务退出原因归为配置缺陷。

此外，faster.nvim 的 LSP 禁用实现调用无参数 `:LspStop`；当前 lspconfig 的原生配置分支会据全局客户端列表调用 `vim.lsp.enable(name, false)`。这提示它可能影响其他正常 buffer，双项目场景仍需专项复现。

实施：在服务启动/附加前执行 buffer 级准入检查，处理已排队的异步附加；需要卸载时只脱离目标 buffer，保留同一客户端服务的其他文件。明确降级后的编辑、撤销和手动恢复行为。

### 3. 签名提示成为主要维护热点

位置：`lua/user/core/blink_signature.lua:1162`。

模块共 1,273 行，混合调用位置解析、参数拆分、重载选择、虚拟文本、浮窗布局和事件调度；直接替换 Blink 内部的 `open_with_signature_help`、`update_position`，还依赖其 trigger/window 状态。现有回归能覆盖许多行为，但升级兼容面仍较大。

实施：先保持现有体验，将解析、显示和 Blink 适配拆开；把内部接口依赖收敛到一个适配模块，增加能力检查、幂等安装与卸载、异常时回退到普通签名浮窗。只有行为用例验证通过后再删除旧实现。

### 4. 项目规则和工具选择需要更一致

位置：`lua/user/plugins/formatting.lua:108`、`lua/user/plugins/lsp.lua:311`、`lua/user/toolchain.lua:120`。

Ruff formatter 硬编码 `--line-length 100`，LSP 设置也写有 100。命令行参数会覆盖项目中的行长设置；例如项目要求 88 列，编辑器保存仍可能使用 100 列。这一优先级由 [Ruff 官方配置文档](https://docs.astral.sh/ruff/configuration/#config-file-discovery) 明确说明。

可执行文件解析已有系统/Mason 逻辑和缓存，但项目内 Node 工具的查找分散在 LSP、formatter、linter 中。项目目录、Java 根目录、测试根目录各有合理差异，需要共享上下文并明确各自的选择理由。

实施：项目配置优先；个人偏好仅作可解释的回退。共享工具解析接口，区分项目工具、系统工具和 Mason 安装工具。缓存键纳入项目/环境，在安装完成、项目切换和环境改变时有明确失效入口。

### 5. 部分模块在功能使用之前已经加载

空启动快照中已经加载 `blink_signature`、`pdf_preview`、AI 路由等自定义模块。打开普通文本会因 lspconfig 对 Blink 的依赖加载补全插件。标注 `InsertEnter` 并不代表插件一定等到插入模式才加载；[lazy.nvim 的加载机制](https://lazy.folke.io/spec/lazy_loading)还包括 Lua 模块引用等触发方式。

实施：保留必要的轻量注册入口，延迟加载复杂实现；单独测量首次使用成本。nvim-treesitter 当前分支明确要求启动加载，应继续遵守其加载约束。以实际耗时决定优化价值，不把减少插件数量本身作为验收目标。

### 6. 使用说明出现漂移

`README.md:11` 仍写 Ctrl-Space 唤起补全；实际配置为 Alt-Space，Ctrl-Space 留给输入法。README 的 Mason 前置依赖还包含 .NET，而当前部署脚本的前置清单没有它。

实施：核对快捷键、依赖和支持矩阵，区分“语法支持”“语言服务”“可运行测试”“可调试应用”。为常用入口建立可由配置导出的键位清单，补充模式与 buffer 局部覆盖说明。

## 分阶段实施

### 第一阶段：修复性能边界，并建立回归入口（P0）

交付：统一 buffer 成本判定、颜色预览保护、buffer 级 LSP 降级、性能复现样例和分组检查入口。

- 检测覆盖总大小、平均行长、单条异常长行，以及打开后通过粘贴形成的长行。
- 让 Treesitter、折叠、颜色、补全、lint、保存格式化共享适用条件，各插件仍保留必要的独立限制。
- 对性能降级给出简短原因和手动恢复入口，避免只显示一个无法解释的布尔标记。
- 将现有回归先拆成可单独运行的主题组，首批加入长行与多 buffer LSP 场景。

验收：30 KB 单行 JSON 在本机同口径中位数争取低于 200 ms；2.5 MiB 文件不会启动被禁用的重型处理；打开大文件不影响另一个正常文件的 LSP；恢复普通文件后补全、诊断、撤销正常。这里的 200 ms 是待验证目标，不是已完成结果。

### 第二阶段：统一项目上下文和工具来源（P1）

交付：`project` 上下文模块、扩展后的工具解析模块、配置健康报告。

- 区分仓库根、语言项目根、当前标签页 cwd 和运行目录；支持嵌套项目、monorepo、worktree、单文件及符号链接。
- 搜索、任务、调试和新终端默认获取相同项目上下文；已有终端显示其真实目录和所属项目。
- AI 终端当前按 provider 缓存，扩展为 provider 与项目的组合；切换项目时仍可找回原会话，并清楚展示当前上下文。
- 统一 Node 本地工具查找；为 Python 区分项目解释器与 debugpy 自身运行环境；继续保留 Java、Rust 的专门策略。
- 提供 `:checkhealth user` 或同类入口，显示生效工具路径、版本、选择原因、缺失依赖及修复入口。
- 使用受控的偏好覆盖入口表达机器差异和功能开关，避免散落新增全局变量；普通项目配置尽量使用工具自身支持的文件。

验收：同一 Neovim 中切换两个不同环境项目，搜索、测试、调试和新终端都使用正确目录及工具；工具安装或环境改变后可刷新，无需靠反复重启诊断原因。

### 第三阶段：完善日常编码流程（P1）

交付：项目优先的语言配置和“编辑—检查—测试—调试”验证样例。

- 移除强制覆盖项目的 Ruff 行长，核对 LSP 与 formatter 的有效配置；格式化保留单一负责人和明确的 fallback。
- 测量保存格式化。当前同步上限为 2,000 ms，可按 formatter 成本调整；手动格式化继续支持较慢工具，避免异步保存引入内容与磁盘不同步。
- 针对常用语言各准备一个小项目，检查补全、跳转、重命名、格式化、诊断、运行测试和断点。
- Python 验证虚拟环境一致；JS/TS/Vue 验证本地工具、Jest/Vitest 选择、源码映射和现有 attach 流程；C/C++ 验证构建产物与 compile_commands；Go、Rust、Java 保留专门适配。
- JS/TS 的 Jest/Vitest 适配按项目实际配置选择，而非仅按 filetype 加载两个适配器；为 monorepo 提供明确选择。
- 利用已有 Overseer 补齐常用 build/run/test 任务，关联失败输出与 quickfix；先检查现有插件支持，再决定是否需要自定义集成。

验收：各目标语言的样例能完成编辑、测试与调试闭环；项目内外使用同一工具时格式化结果一致；不支持的操作给出具体原因。

### 第四阶段：控制复杂模块的升级成本（P1）

交付：签名提示模块拆分、浮窗职责划分、按需加载的 PDF/AI 实现。

- 签名提示拆为调用解析、参数/重载处理、渲染、Blink 适配四部分；优先建立接口边界，避免只按行数机械拆文件。
- 统一事件资源的注册与清理约定；取消过时请求，处理 buffer 删除、窗口关闭、快速切换和配置重载。
- 浮窗模块负责样式与布局，功能模块负责内容，关闭入口负责生命周期；减少多个模块反复改同一窗口。
- PDF 保留轻量的文件读取与命令注册入口，首次使用时加载渲染实现；继续验证已有缓存限制、文件监听和渲染任务回收。
- 工具清单、语言配置、测试/DAP 选择逐步共享数据，避免一次性重写所有插件 spec。

验收：签名的嵌套调用、重载、多行参数、CJK/Unicode、snippet 跳转和窗口缩放均通过；适配失效时编辑器仍可用；关闭或重载后无残留浮窗、重复回调、文件监听和渲染任务。

### 第五阶段：统一界面与键盘体验（P2）

交付：交互约定、窗口尺寸规则、真实终端验收清单。

- 以现有主题、颜色语义和布局模块为基础，覆盖补全、签名、hover、诊断、picker、通知和左右面板。
- 在 80×24、120×36、宽屏三档尺寸下检查；面板过多时为正文保留可用宽度，通知和虚拟行不遮挡核心操作。
- 保留 Esc 的现有语义，核对输入法、Alt 键、终端 Ctrl-/、snippet 和多光标的模式差异。
- 审查 LSP 的 `gr` 等映射与内置映射的前缀关系；只有复现延迟或冲突才调整，并保留清楚的迁移说明。
- 统一 buffer 关闭行为，验证多窗口布局、修改未保存的文件、固定面板和会话恢复。
- 明确 AI provider 的能力差异；只在支持相应操作时展示可执行入口，保持现有外部改动与 diff 工作流。
- 图片/PDF 按终端真实能力选择内联或外部查看；验证无图形协议、SSH 和缺少可选工具时的行为。

验收：常用操作无需猜测关闭键或作用范围；四个现有主题均能辨认选中项、诊断和签名；小窗口中编辑区可用；真实终端操作与文档一致。

### 第六阶段：让更新、部署和维护可重复（P2，基础检查随前述阶段推进）

交付：分层 CI、部署验证、维护说明和更新流程。

- 静态检查、无头行为回归、需要 UI 的交互验收分别报告结果。测试重点放在用户行为、生命周期和故障边界，减少只镜像颜色常量或配置结构的断言。
- CI 使用已验证的 Neovim 版本、插件锁和必要 parser；依赖准备与离线测试分开，状态、缓存与数据目录明确隔离。
- 增加项目 A/B、长行、缺少可选依赖、会话恢复和核心键位覆盖检查；对所有语言安装完整工具链留作独立验证任务。
- 部署支持计划预览、明确的配置/Neovim 版本选择和可读失败状态。当前部分安装失败只告警后仍显示完成，应准确区分完整成功与部分完成。
- 按功能或语言选择安装工具，默认方案继续覆盖现有功能；记录实际调用版本与 Mason 锁定安装版本的区别。
- 每次更新插件锁时检查相关改动并运行对应回归；提供上一个可用锁与配置提交的恢复步骤。
- 修正 README 漂移，补充最常见工作流、依赖说明、问题诊断和实际支持范围。

验收：干净环境按指定版本部署可重现；缺少非必要工具不妨碍基本编辑；部署部分失败有可定位报告；升级失败可恢复到前一个可用组合。

## 建议实施粒度

按以下顺序提交独立、可回退的改动，每步附对应验证证据：

1. 长行判定与颜色扫描保护。
2. buffer 级 LSP 降级及双项目回归。
3. 回归分组、性能脚本和最小 CI。
4. 项目上下文与工具来源报告。
5. formatter/LSP 项目规则一致性。
6. 常用语言的测试、调试和任务集成。
7. 签名提示适配层与内部拆分。
8. PDF/AI 按需加载与生命周期整理。
9. 界面、键位、buffer 和会话交互验收。
10. 部署恢复、依赖选择与文档收尾。

首批完成标准：消除已复现的单行 JSON 秒级卡顿；大文件降级仅影响目标 buffer；修正文档的补全键位，并让这些行为进入持续回归。
